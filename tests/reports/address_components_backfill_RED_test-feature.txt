DIAGNOSIS: a genuine defect, not an environment/setup artifact. Behave loads
every step-definitions file across the WHOLE repo globally (not scoped per
feature), so a step text pattern registered in this feature's new step file
collided with an EXISTING, already-merged step in the sibling
venue-address-components.feature's own step file
(tests/bdd/steps/venue_address_components_steps.py), which hardcodes the
literal string '"Casa Bacurau" is a venue with a Google place id' for its
own (unrelated) Google Places Details scenario. A second, identical
collision existed on 'Google Places returns address components with
sublocality level 1 "{value}"' — an EXACT duplicate of the sibling file's
own parametrized pattern for the SAME reason.

FIX APPLIED: renamed this feature's own step wording (both the .feature
file's Gherkin text and the corresponding step-definition decorators) to
disambiguate from the sibling without changing any assertion or behavior:
  - "X is a venue with a Google place id" -> "X has a Google place id"
    (only the two occurrences that lacked the "and no stored address
    components" suffix already making them unique)
  - "Google Places returns address components with sublocality level 1 X"
    -> "Geocoding returns address components with sublocality level 1 X"
    (this feature's Given programs geocode_by_place_id, a DIFFERENT client
    method from the sibling's get_place_details, so the rename also makes
    the step text honestly describe which Google API family answers it)

After the rename, the very next run went green on all 15 scenarios — see
address_components_backfill_GREEN_test-feature.txt. The underlying parser/
precedence/backfill-service LOGIC itself was never the source of this
failure (it was independently proven correct beforehand by the pytest
suites cited above); this failure was a Behave step-registration collision,
caught and fixed exactly as Phase 6 ("diagnose before editing again")
prescribes.
